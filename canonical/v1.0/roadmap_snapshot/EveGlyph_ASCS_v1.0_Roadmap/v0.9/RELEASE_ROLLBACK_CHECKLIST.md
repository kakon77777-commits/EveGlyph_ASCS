# v0.9 Release / Rollback Checklist

## Before release

- freeze version/schema matrix;
- run all profile validators and compatibility vectors;
- run canonical source UTF-8 / LF / control / hash gates;
- build package from a clean tree;
- generate package SHA-256 manifest;
- record dependency/runtime versions;
- implementation builds: produce SBOM (SPDX stable profile acceptable) and supply-chain provenance/attestation where available;
- execute migration dry-run against supported previous release;
- execute rollback rehearsal;
- record known issues and unsupported profiles;
- verify no secrets, caches, private absolute paths, temporary tokens, or generated bytecode are shipped.

## Rollback requirements

A release MUST identify a verified rollback target. Rollback MUST NOT silently rebind immutable object/revision/content addresses. If a newer canonical profile cannot be read by the older binary, rollback requires a forward-preserving reader, explicit reverse migration, or read-only preservation mode; deleting unknown state is not rollback.

## Release health

The package must support an offline health check over schemas, manifests, hashes, validators, examples, and compatibility records without requiring model/network access.
