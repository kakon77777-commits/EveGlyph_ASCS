# v0.2｜Contract Hardening & Compatibility Freeze

**English Title:** EveGlyph ASCS v0.2 Contract Hardening & Compatibility Freeze  
**作者：** Neo.K / EveMissLab  
**版本：** v0.2  
**日期：** 2026-08-24  
**前置基線：** ASCS v0.1 Architecture Complete；MVP-01 v0.1

---

## 摘要

ASCS v0.1 已建立 object identity、revision DAG、spatial syntax、native math、glyph compilation、multi-layer addressing、EGIR、EGStore 與 EGCR；但 v0.1 仍缺少一個跨所有層的版本／相容性治理模型。如果未來 EGIR schema、math profile、glyph profile、storage manifest、runtime command 或 agent capability 各自升版，卻沒有明確的 compatibility contract，則系統可能出現最危險的一類錯誤：**舊資料仍然可以被讀入，但被新程式以不同語義解讀。**

v0.2 因此不增加新的 ontology；它建立一個跨層 compatibility envelope，保證未來版本升級必須是 explicit、可驗證、可拒絕、可遷移，而不是 silent reinterpretation。

核心原則：

$$
\boxed{
\text{Same Bytes}
+\text{Different Semantics}
=\text{Incompatible Unless Explicitly Migrated}
}
$$

---

# 1. Layer Version Tuple

一份完整 EveGlyph runtime state 至少應宣告：

$$
V=
(V_{ASCS},V_{EGIR},V_{EGStore},V_{EGCR},V_{NCM},V_{Glyph},V_{Agent}).
$$

v0.2 建議初始 baseline：

```text
ASCS      = ascs/0.2
EGIR      = egir/0.1
EGStore   = egstore/0.1
EGCR      = egcr/0.1
NCM       = ncm/0.1
Glyph     = glyph/0.1
Agent     = agent-contract/0.1
```

ASCS release version 與各 subsystem schema version MUST 分離。整體產品升到 v0.3，不代表所有 schema 都必須同步升版。

---

# 2. Compatibility Classes

兩個版本 $A,B$ 的 compatibility 不使用單一 boolean，而定義：

$$
Compat(A,B)
\in
\{
Exact,
Backward,
ForwardPreserve,
Migratable,
Incompatible
\}.
$$

## 2.1 Exact

兩端對 canonical semantics 的理解相同。

## 2.2 Backward

新版 reader 能完整理解舊版資料且不重新解釋既有欄位。

## 2.3 ForwardPreserve

舊 reader 不理解新 extension，但能安全保留並 round-trip unknown extension，而不執行它。

## 2.4 Migratable

需要顯式 migration：

$$
M_{A\rightarrow B}:State_A\rightarrow State_B.
$$

## 2.5 Incompatible

不存在被規格承認的安全解讀或 migration path。Reader MUST 拒絕。

---

# 3. No Silent Reinterpretation

v0.2 最核心不變量：

> **任何既有欄位、predicate、operator、address type、capability name、hash preimage 或 execution meaning，不得在相同 version identifier 下改變語義。**

如果語義改變，至少必須做一項：

1. 新 schema/profile version；
2. 新 predicate/operator ID；
3. 新 canonicalization version；
4. 顯式 migration record。

禁止：

$$
bytes_A=bytes_B
$$

但在沒有升版的情況下：

$$
Meaning_A\neq Meaning_B.
$$

---

# 4. Migration Contract

Migration record：

$$
MRecord=
(id,from,to,tool,version,inputHash,outputHash,fidelity,diagnostics,provenance).
$$

Migration MUST：

- 指定 source/target profile；
- deterministic，或明確標記 nondeterministic candidate phase；
- 保存 input/output hashes；
- 保存 tool/version；
- 回報 fidelity；
- 對 unresolved/ambiguous mapping 不強迫成功；
- 不覆寫原始 artifact。

合法 fidelity：

```text
exact
lossless-structural
semantic-subset
approximate
partial
unknown
```

---

# 5. Canonicalization Versioning

TW-01 已定義：

```text
egir-cj/0.1
```

任何 hash-covered canonicalization 行為改變都 MUST 使用新 version，例如：

```text
egir-cj/0.2
```

不得在 `egir-cj/0.1` 名稱下修改 key ordering、numeric lowering、Unicode treatment 或 set-sorting rules。

因此：

$$
C_{0.1}(x)\neq C_{0.2}(x)
$$

是合法的，只要 version qualification 明確。

---

# 6. Hash Domain Stability

v0.1 已有 content / revision / workspace domain separation。v0.2 再凍結：

$$
DomainName+Version
$$

本身就是 hash contract 的一部分。

既有 domain separator 不得重新使用於不同 preimage semantics。

若 preimage 改變：

$$
D_{old}\neq D_{new}.
$$

---

# 7. Extension Namespace

Extension key MUST namespace-qualified，例如：

```text
org.evemisslab.spatial-grammar/0.1
org.evemisslab.math-proof/0.1
org.example.plugin/1
```

禁止 generic global keys：

```text
plugin
extra
data2
custom
```

除非它們是 core schema 明確欄位。

未知 extension：

- Reader MUST preserve；
- Runtime MUST NOT execute；
- Writer SHOULD round-trip unchanged；
- Critical extension 若不支援 MUST 拒絕進入需要該語義的操作。

---

# 8. Feature Negotiation

Runtime feature descriptor：

$$
F=(name,version,status,critical).
$$

例如：

```json
{
  "name": "native-math",
  "version": "ncm/0.1",
  "status": "supported",
  "critical": true
}
```

Load 流程：

$$
BundleFeatures
\rightarrow
CompareCapabilities
\rightarrow
\{Load,LoadPreserveOnly,RequireMigration,Reject\}.
$$

不得「能 parse JSON 就算支援」。

---

# 9. Capability Versioning

TW-03 capability name，例如：

```text
workspace.read
workspace.write
runtime.execute
relation.promote
```

一旦公開，不得在相同 capability name 下擴大 authority。

如果 authority meaning 改變，必須：

- 新 capability name；或
- capability profile version。

因此：

$$
CapabilityName
\rightarrow
StableAuthorityMeaning.
$$

---

# 10. Predicate / Operator Stability

例如：

```text
eg:dependsOn
eg:represents
eg:bindsOperator
```

已發布 predicate 的 source/target semantics 不得 silent change。

Native Math operator 也必須以 semantic operator identity / theory version 綁定，而不是只靠 visible glyph/name。

---

# 11. Deprecated ≠ Removed

Lifecycle：

$$
Experimental
\rightarrow
Stable
\rightarrow
Deprecated
\rightarrow
RemovedInNewMajor.
$$

在 v0.x 期間仍可有 breaking changes，但 MUST：

- 顯式升版；
- 提供 migration 或明確拒絕；
- 不 silent reinterpret。

在 v1.0 之後，任何 break v1 canonical contract 的變更必須進 v2 或明確 major-version path。

---

# 12. Golden Vectors Governance

每個 canonical subsystem SHOULD 有不可任意改寫的 golden vectors：

- EGIR canonical/hash vectors；
- EGStore chunk/manifest vectors；
- EGCR transaction vectors；
- NCM semantic/equality vectors；
- Glyph structure/binding vectors；
- Agent candidate/promotion vectors。

若新版 implementation 使舊 stable vector 改變，必須先判定：

$$
BugFix?
\quad\text{or}\quad
SemanticBreak?
$$

若是 semantic break，必須升版。

---

# 13. Release Artifact Obligations

從 v0.2 起，每個 round release SHOULD 至少包含：

```text
VERSION.md
CHANGELOG.md
COMPATIBILITY.md
MIGRATIONS.md
VALIDATION.md
SHA256SUMS.txt
```

若本輪沒有 migration，`MIGRATIONS.md` 必須明確寫：

```text
No canonical migration required in this round.
```

不能省略後讓本地端猜測。

---

# 14. Compatibility Matrix

每輪都更新：

| Producer | Consumer | Result |
|---|---|---|
| egir/0.1 | egir/0.1 reader | Exact |
| egir/0.1 + unknown noncritical extension | preserving reader | ForwardPreserve |
| future egir/0.2 breaking core | egir/0.1 reader | Reject / Migration Required |
| egstore/0.1 identity | egstore/0.1 reader | Exact |
| egstore/0.1 Brotli | reader without Brotli | UnsupportedCodec, not InvalidIdentity |
| ncm/0.1 | runtime without native math | PreserveOnly / UnsupportedExecution |

這個 matrix 本身將成為 v1.0 handoff 必備資產。

---

# 15. Reader Decision Procedure

收到 bundle $B$：

$$
ParseVersion(B)
\rightarrow
CheckCriticalFeatures
\rightarrow
CheckCompatibility
\rightarrow
\begin{cases}
Load\\
PreserveOnly\\
Migrate\\
Reject
\end{cases}
$$

任何 `Reject` 都應 typed diagnostic，不應 fallback 成「盡量猜」。

---

# 16. Write Decision Procedure

Writer 在修改既有 artifact 前 MUST 知道：

- source version；
- target version；
- 是否會升版；
- 是否有 migration；
- unknown extensions 是否能保留；
- write 後舊 reader 會得到什麼結果。

若無法保證，writer MUST 不 overwrite 原 artifact。

---

# 17. AI Migration Boundary

AI 可以：

- 建議欄位 mapping；
- 建議 semantic migration；
- 產生 candidate diagnostics；
- 協助生成 migration plan。

AI 不可以在未驗證下：

$$
UnknownOldMeaning
\rightarrow
InventedNewCanonicalMeaning.
$$

AI-assisted migration 必須先產生 candidate，最終 migration output 仍需 schema、hash、semantic validators。

---

# 18. v0.2 不新增 canonical migration

本輪是治理契約硬化，不改 TW-01 `egir/0.1`、TW-02 `egstore/0.1`、TW-03 `egcr/0.1` 的既有 canonical semantics。

因此：

```text
No canonical migration required from ASCS v0.1 package to v0.2 governance layer.
```

v0.1 artifacts 仍是 v0.2 的直接 baseline。

---

# 19. v0.2 Design Freeze

1. ASCS release version 與 subsystem schema/profile version 分離。
2. Version tuple 必須可被明確列出。
3. Compatibility 不使用單一 boolean。
4. `Exact / Backward / ForwardPreserve / Migratable / Incompatible` 五類正式存在。
5. 相同 version identifier 下禁止 semantic reinterpretation。
6. Migration 必須有 source/target、hash、tool/version、fidelity、provenance。
7. Migration 不覆寫原始 artifact。
8. Canonicalization 行為變更必須升 canonicalization version。
9. Hash preimage meaning 變更必須使用新 domain/version。
10. Extension key 必須 namespace-qualified。
11. Unknown extension 預設 preserve，不自動 execute。
12. Critical unsupported feature 必須 reject 或 require migration。
13. Capability name 不得 silent 擴權。
14. Predicate/operator semantics 不得 silent 改義。
15. Deprecation 與 removal 分離。
16. Stable golden vectors 不得無理由漂移。
17. 每輪 release 必須更新 compatibility / migration / validation record。
18. Reader 必須能回 Load / PreserveOnly / Migrate / Reject。
19. Writer 不得在相容性未知時 overwrite 原 artifact。
20. AI migration output 預設 candidate，不能直接變 canonical truth。
21. v0.2 本身不要求 v0.1 canonical migration。
22. v1.0 handoff 必須帶完整 compatibility matrix。

---

# 20. Conformance Questions

未來每輪至少回答：

1. 這一版改了哪個 layer version？
2. 哪些舊資料仍 Exact？
3. 哪些是 Backward？
4. 哪些只能 ForwardPreserve？
5. 哪些需要 Migration？
6. 哪些必須 Reject？
7. 是否改 canonicalization？
8. 是否改 hash preimage？
9. 是否新增 critical extension？
10. 是否擴大 capability authority？
11. 是否改 predicate/operator meaning？
12. 是否讓任何 stable golden vector 漂移？

任何一項無法回答，就不能宣稱該 round 已封版。

---

# 21. v0.2 完成判準

v0.2 不以新增 UI 或 runtime feature 作成功標誌。

成功標誌為：

$$
\boxed{
\text{Future Versions Can Change Without Making Old Data Ambiguous.}
}
$$

當未來 v0.3–v1.0 每一版都能清楚說明「讀什麼、保留什麼、遷移什麼、拒絕什麼」，v0.2 的任務就完成。

---

# 22. 下一輪接口：v0.3

v0.3 將在本 compatibility envelope 之下正式處理：

$$
\boxed{
\text{Persistent Editing}
+\text{History}
+\text{Branch/Merge}
+\text{Conflict}
}
$$

重點不再是 schema 版本，而是讓長期編輯歷史成為 canonical、可恢復、可合併又不破壞 Paper 01 identity model 的 runtime contract。
