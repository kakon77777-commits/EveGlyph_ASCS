# 摘要

ASCS v0.1 已經具有 persistent object identity、immutable revision、workspace revision、branch heads、event/provenance 與 stale-write conflict；但這些能力仍不足以成為長期 local-first 編輯模型。真正的長期工作區必須回答：多個 session 同時編輯時哪些操作可以自動合併？同一 object 的 content edit 與 Canvas move 能否獨立合併？兩個 AI 同時修改同一公式時應建立 branch、conflict 還是 last-write-wins？Autosave 是否等於產生 canonical commit？Undo 是否能抹掉歷史？Crash 後未提交修改怎麼恢復？一個已被引用的 revision 是否可以被 squash？

v0.3 提出 **Persistent Editing History Model, PEHM**。PEHM 將編輯歷史分成三個互不偷換的層級：

1. **Intent / Command History**：人類、AI 或 system 曾經提出的命令，包括 accepted、rejected、conflict、cancelled；
2. **Canonical Commit DAG**：真正形成 workspace revision 的不可變歷史；
3. **Session Navigation**：UI-level undo stack、selection history、draft navigation 等非 canonical state。

Canonical workspace history 定義為 DAG：一般 commit 有一個 parent，merge commit 可以有多個 parents。Branch 是指向 workspace revision 的 mutable reference，不是另一份 object ontology；Workspace Fork 才建立新的 workspace identity。對 merge，v0.3 不採用「對整份 JSON 做 last-write-wins」的粗糙模型，而是把 workspace mutation 拆成多個 merge channel：object intrinsic content、placement、relation、alias/metadata、tombstone/lifecycle。不同 channel 的獨立修改可以自動組合，例如一個 session 修改公式內容、另一個 session 只移動同一 node，應無衝突地得到「新內容 + 新位置」。相反地，兩邊都修改同一 object intrinsic content、同時移動同一 placement、或 delete-vs-edit，若 domain-specific merge 無法 deterministic 解決，就必須產生 first-class conflict object。

v0.3 進一步定義 `org.evemisslab.history/0.1` extension profile、stable branch identity、conflict object profile、merge attempt、conflicted merge workspace、resolution commit、canonical revert、autosave draft、checkpoint commit、recovery capsule、rebase provenance、history compaction 與 retention boundary。Undo/redo 被分成 session-local navigation 與 canonical revert；對已 commit 的歷史，undo MUST 建立新的 inverse commit，而不是刪掉既有 revision。Autosave 預設只保存 recovery draft，不等於 canonical commit；Checkpoint 才建立新的 workspace revision。

v0.3 的最終目的不是實作 CRDT 或 Git clone，而是凍結一個更底層的語義邊界，使未來本地端可以自由選擇三方合併、CRDT、OT、operation log、Git-like DAG 或資料庫 transaction，而不改變「什麼叫同一 object、同一 revision、真正 commit、conflict、revert、recovery」的 canonical meaning。

# 3. 三層 History Model

定義：

$$
H=(H_I,H_C,H_S).
$$

其中：

- $H_I$：Intent / Command History；
- $H_C$：Canonical Commit DAG；
- $H_S$：Session-local Navigation History。

## 3.1 Intent / Command History

命令紀錄：

$$
q=(q_{id},actor,base,type,payload,status,diagnostics,time).
$$

`status` 可以是：

```text
proposed
accepted
rejected
conflict
cancelled
failed-before-commit
```

被拒絕的命令可以保留 audit record，但：

$$
q\in H_I
\not\Rightarrow
q\in H_C.
$$

也就是「某 AI 曾經想改」不等於「世界真的被改過」。

## 3.2 Canonical Commit DAG

Canonical workspace history：

$$
H_C=(V_W,E_W).
$$

每個 node 是 immutable workspace revision：

$$
W_i.
$$

一般 commit：

$$
Parents(W_{n+1})=\{W_n\}.
$$

Merge commit：

$$
Parents(W_m)=\{W_a,W_b\}.
$$

Root：

$$
Parents(W_0)=\varnothing.
$$

## 3.3 Session Navigation

Session history 包括：

- temporary undo stack；
- redo stack；
- selection history；
- viewport history；
- uncommitted text buffer history；
- drag preview history。

它們預設不進 workspace revision：

$$
H_S\not\subseteq H_C.
$$

---

# 4. Workspace Commit 是 Atomic Canonical Unit

一個 canonical workspace commit：

$$
K=(W_{base},\Delta_O,\Delta_R,\Delta_P,\Delta_M,E).
$$

其中：

- $\Delta_O$：object head / revision changes；
- $\Delta_R$：relation changes；
- $\Delta_P$：placement changes；
- $\Delta_M$：workspace metadata / alias / lifecycle changes；
- $E$：provenance event(s)。

Commit 必須 atomic：

$$
Commit(K)
\rightarrow
\begin{cases}
W_{new} & \text{all canonical validations pass}\\
Failure & \text{canonical state unchanged}
\end{cases}
$$

不得出現「object content 已 commit，但 placement / relation 一半失敗」而仍宣稱同一 transaction 成功。

---

# 5. Optimistic Base-Revision Discipline

每個 canonical command MUST pin：

$$
base\_workspace\_revision.
$$

若：

$$
W_{current}\neq W_{base},
$$

預設結果：

$$
StaleWrite\rightarrow Conflict.
$$

Runtime MAY 依 policy：

- auto-create branch；
- request rebase；
- run deterministic merge preflight；

但 MUST NOT silent last-write-wins。

---

# 6. Branch Model

Branch 是 mutable head reference：

$$
B=(b_{id},name,head,createdFrom,status,metadata).
$$

其中：

- `branch_id` MUST stable；
- `name` 是 mutable alias；
- `head` 指向 immutable workspace revision；
- rename 不改 `branch_id`。

TW-01 `workspace.heads` 的 branch-name mapping 可以繼續作 portable core representation；v0.3 stable branch metadata SHOULD 放在：

```text
extensions["org.evemisslab.history/0.1"].branches
```

## 6.1 Branch 不建立新 workspace identity

$$
Branch(W)\Rightarrow A^{id}(W)\text{ unchanged}.
$$

## 6.2 Branch Name 不是 immutable citation

引用 reproducible history MUST 使用 workspace revision address，而不是 branch name：

$$
/main\neq W_{immutable}.
$$

---

# 7. Fork Model

v0.3 區分三種 fork。

## 7.1 Branch Fork

同 workspace identity 下建立新 branch：

$$
ForkBranch(W_i)\rightarrow B_j.
$$

## 7.2 Workspace Fork

建立新 workspace persistent identity：

$$
ForkWorkspace(W_i)
\rightarrow
W'_0,
$$

並保存：

$$
forkedFrom(W'_0,W_i).
$$

## 7.3 Object Fork

沿用 Paper 01：新 object identity + lineage。

三者不得被 UI 統一叫「duplicate」後丟失語義。

---

# 8. Merge Base

兩個 heads $W_L,W_R$ 的 merge MUST 明確選擇 base：

$$
W_B=LCA(W_L,W_R)
$$

或由 caller 顯式提供可驗證 base。

若存在多個合理 merge bases，runtime MUST：

- deterministic select by declared policy；或
- 回 `AmbiguousMergeBase`。

不得依 unordered filesystem/database iteration 隨機選一個。

---

# 9. Merge 不是整份 JSON 的單一操作

Workspace merge 定義為多 channel：

$$
Merge=
M_O\oplus M_P\oplus M_R\oplus M_A\oplus M_L.
$$

其中：

- $M_O$：object intrinsic/revision merge；
- $M_P$：placement merge；
- $M_R$：relation merge；
- $M_A$：alias/metadata merge；
- $M_L$：lifecycle/tombstone merge。

這是 v0.3 的核心工程決策之一。

---

# 10. Independent-Dimension Auto Merge

若 left 只改 object intrinsic，right 只改同 object placement：

$$
L:\Delta_O(o)\neq\varnothing,\quad \Delta_P(o)=\varnothing
$$

$$
R:\Delta_O(o)=\varnothing,\quad \Delta_P(o)\neq\varnothing
$$

則 SHOULD 自動合併：

$$
Merged(o)=Content_L+Placement_R.
$$

不應因「同一 node 被兩邊碰過」就產生假 conflict。

同理，兩邊修改不同 persistent objects 或不同 relations，通常可 union。

---

# 11. Object Intrinsic Merge

對 object $o$，base / left / right revisions 為：

$$
v_B,v_L,v_R.
$$

## 11.1 One-sided change

若：

$$
v_L=v_B,\quad v_R\neq v_B,
$$

則選 $v_R$。

## 11.2 Identical change

若：

$$
v_L=v_R,
$$

直接選該 revision。

## 11.3 Concurrent distinct change

若：

$$
v_L\neq v_B,\quad v_R\neq v_B,\quad v_L\neq v_R,
$$

則只有在 object kind 的 versioned merge profile 能 deterministic 三方合併時，才可產生：

$$
v_M=MergeKind_k(v_B,v_L,v_R).
$$

新 object revision MUST：

$$
Parents(v_M)=\{v_L,v_R\}.
$$

若無合法 kind-specific merge：

$$
Result=ConflictObject.
$$

---

# 12. Placement Merge

Placement 是 workspace extrinsic state，因此與 object revision merge 分離。

## 12.1 One-sided move

Base $p_B$，left $p_L$，right $p_R$：

若：

$$
p_L=p_B,\quad p_R\neq p_B,
$$

則選 $p_R$。

## 12.2 Same resulting move

若：

$$
p_L=p_R,
$$

可直接接受。

## 12.3 Concurrent different move

若：

$$
p_L\neq p_B,\quad p_R\neq p_B,\quad p_L\neq p_R,
$$

預設 MUST 產生 placement conflict。

禁止 default：

- arbitrary left/right winner；
- coordinate average；
- timestamp last-writer-wins。

Domain profile MAY 定義 deterministic special policy，但必須顯式版本化。

---

# 13. Relation Merge

Relation 是 first-class persistent object，因此 intrinsic relation edit 原則上遵循 object merge。

但是 relation merge validator MUST 額外檢查：

- source/target 是否仍存在；
- predicate schema 是否一致；
- tombstone 是否使 edge dangling；
- authority class 是否被降級/升級；
- derived candidate 是否被錯誤升格成 explicit。

兩邊分別新增不同 relation identities 可以 union。

同一 relation identity 被兩邊改成不同 predicate/target，若無 deterministic merge，MUST conflict。

---

# 14. Tombstone / Lifecycle Merge

最危險的案例之一：

$$
L:Tombstone(o)
$$

$$
R:Edit(o)
$$

預設：

$$
DeleteVsEdit\rightarrow Conflict.
$$

同理：

$$
DeleteVsMove\rightarrow Conflict.
$$

如果兩邊都 tombstone 同一 object，且 tombstone semantics 相容，可合併。

不得因 timestamp 較新就自動刪掉另一邊有效修改。

---

# 15. Alias / Metadata Merge

Human-facing alias 與 metadata 不應影響 persistent identity。

Alias merge 可以有專用政策，但：

- 同名指向不同 identity MUST conflict or preserve both with namespace disambiguation；
- mutable alias 不能改寫 immutable citation；
- metadata merge 不得改 hash-covered intrinsic content，除非該 metadata 本來就在 corresponding canonical preimage 中。

---

# 16. Conflict Object

v0.3 將 conflict 定義為 first-class canonical object，而不是只存在 UI memory。

建議 kind：

```text
org.evemisslab.conflict
```

profile：

```text
org.evemisslab.history-conflict/0.1
```

最小 intrinsic：

```json
{
  "profile": "org.evemisslab.history-conflict/0.1",
  "conflict_type": "object-content",
  "base_workspace_revision": "wrev:...",
  "left_workspace_revision": "wrev:...",
  "right_workspace_revision": "wrev:...",
  "target": {"type": "identity", "value": "urn:uuid:..."},
  "base": {},
  "left": {},
  "right": {},
  "status": "unresolved",
  "resolution": null
}
```

合法 `conflict_type` 至少：

```text
object-content
placement
relation
lifecycle
alias
subobject
merge-base
```

---

# 17. Conflicted Merge Workspace

v0.3 允許「merge 尚未解完但必須保存」成為 canonical recovery state。

流程：

$$
MergeAttempt(W_L,W_R)
\rightarrow
W_C+\{Conflict_i\}.
$$

其中 $W_C$ 可以被標記：

```text
history_status = conflicted
```

此狀態可以：

- save；
- close application；
- crash/recover；
- transfer to another session；
- continue conflict resolution。

但 runtime SHOULD 阻止受 unresolved conflict 影響的 executable semantics 進入 normal execution。

---

# 18. Conflict Resolution

Resolution command：

$$
ResolveConflict(c,r,actor,base)
\rightarrow
new\ revision/event.
$$

Resolution 類型可以是：

```text
take-left
take-right
manual-merged-value
kind-specific-merge
keep-both
custom-versioned-policy
```

Resolution MUST 保存：

- conflict ID；
- actor；
- chosen policy；
- generated revisions；
- evidence/diagnostics；
- event provenance。

當所有 critical conflicts resolved，才可形成 final merge commit：

$$
Parents(W_M)=\{W_L,W_R\}.
$$

---

# 19. Merge Commit Provenance

Merge event SHOULD 記錄：

```text
merge_base
left_parent
right_parent
merge_policy_version
auto_merged_channels
conflict_ids
resolution_events
result_workspace_revision
```

未來本地端必須能回答：

> 為什麼這個 merge 沒有 conflict？

> 哪些欄位是自動合併？

> 哪些衝突由誰決定？

---

# 20. Rebase Semantics

Rebase 是建立新 revision sequence，不是修改舊 immutable revisions。

$$
Rebase(B_{old},onto=W_t)
\rightarrow
B_{new}.
$$

每個新 commit SHOULD 保存：

$$
rebasedFrom(W_{old}).
$$

舊 revisions 在 retention policy 允許前仍存在。

因此：

$$
Rebase\neq InPlaceHistoryMutation.
$$

---

# 21. Undo 分成兩種

## 21.1 Session Undo

對尚未 canonical commit 的 draft：

$$
Undo_{session}
$$

只操作 session overlay / draft buffer。

## 21.2 Canonical Revert

對已 commit revision：

$$
Revert(W_t,target=W_k)
\rightarrow
W_{t+1}.
$$

它建立新的 inverse commit。

歷史保留：

$$
W_k\in H_C.
$$

禁止 UI 將「Undo」實作成直接刪除已 commit canonical revision。

---

# 22. Redo

Session redo 可恢復尚未 commit 的 local draft step。

Canonical redo 則是新的 forward commit，例如重新套用被 revert 的 change：

$$
Redo_{canonical}
\rightarrow
W_{new}.
$$

它仍不是把 branch pointer 偷偷移回舊狀態而假裝沒有中間歷史。

---

# 23. History Rewrite Boundary

v0.3 正式區分：

```text
unpublished-local
shared
anchored
```

## 23.1 Unpublished Local

可以進行 branch ref reset/rebase，但 immutable revisions 本身仍不被修改。

## 23.2 Shared

若 revision 已被其他 session/workspace 消費，rewrite SHOULD 改用 new branch / rebase lineage，而不是讓既有 reference 漂移。

## 23.3 Anchored

若 revision 已被 stable address、release、proof citation、external reference 或 archive manifest 錨定：

$$
RewriteInPlace=Forbidden.
$$

---

# 24. Autosave 不等於 Canonical Commit

v0.3 定義兩種保存。

## 24.1 Autosave Draft

Autosave draft：

$$
D=(session,base,pendingCommands,draftHash,time,toolVersion).
$$

它的目的：crash recovery。

它 MUST NOT 自動被當作 workspace commit DAG 的新 node。

## 24.2 Checkpoint Commit

Checkpoint 才建立：

$$
W_{n+1}.
$$

因此 UI 可以頻繁 autosave，而不必每次 keypress 都污染 canonical history。

---

# 25. Checkpoint Semantics

Checkpoint 可以由：

- user explicit save；
- agent patch accept；
- transaction boundary；
- policy-based periodic checkpoint；
- before external effect；
- before risky migration；
- before merge/rebase。

觸發。

Checkpoint MUST：

1. pin base revision；
2. validate pending canonical mutations；
3. create event/provenance；
4. compute new hashes；
5. persist through TW-02 durability policy；
6. only then move branch head。

---

# 26. Recovery Capsule

v0.3 建議 recovery profile：

```text
org.evemisslab.recovery/0.1
```

最小 recovery capsule：

```json
{
  "profile": "org.evemisslab.recovery/0.1",
  "session_id": "...",
  "workspace_id": "urn:uuid:...",
  "base_workspace_revision": "wrev:...",
  "last_observed_head": "wrev:...",
  "pending_commands": [],
  "draft_state_hash": "sha256:...",
  "created_at": "...",
  "tool": {"name": "...", "version": "..."}
}
```

Capsule 是 recovery artifact，不是 canonical workspace commit。

---

# 27. Session Recovery Decision Procedure

Crash 後：

$$
LoadCanonicalHead
\rightarrow
LoadRecoveryCapsule
\rightarrow
CompareBase.
$$

## Case A — Head unchanged

若：

$$
W_{head}=W_{base},
$$

runtime MAY replay pending commands through normal validation pipeline。

## Case B — Head advanced

若：

$$
W_{head}\neq W_{base},
$$

runtime MUST NOT silent replay onto new head。

合法策略：

- create recovery branch from base；
- rebase pending commands；
- merge and surface conflicts。

## Case C — Base missing

回：

```text
RecoveryBaseUnavailable
```

不得猜測近似 base。

---

# 28. External Effects 不自動 Replay

Recovery capsule 中若存在 external-effect command，例如：

- send network request；
- write external file；
- spawn process；
- call payment/API；

crash recovery MUST NOT 自動 replay，除非 operation 明確具有 idempotency key 與 safe retry profile。

預設：

$$
ExternalEffectRecovery\rightarrow Manual/PolicyDecision.
$$

---

# 29. Autosave / Checkpoint / External Effect Ordering

高風險 external effect SHOULD 使用：

$$
Checkpoint
\rightarrow
AuthorizeEffect
\rightarrow
AttemptEffect
\rightarrow
ObserveOutcome
\rightarrow
CommitProvenance.
$$

這樣 crash 後至少知道 effect 是從哪一個 canonical world state 發出。

---

# 30. History Compaction 分四層

v0.3 禁止把所有「compact」混成 squash。

## 30.1 Physical Storage Compaction

TW-02 層：repack/recompress/GC physical chunks。

若 decoded canonical history不變：

$$
Allowed.
$$

## 30.2 Derived Index Compaction

R-tree、search index、cache 可以自由重建。

## 30.3 Intent Log Compaction

Rejected/cancelled/noncanonical command audit 可依 retention policy summary/prune，只要不冒充 commit history。

## 30.4 Canonical History Compaction

對 immutable commit DAG：

$$
InPlaceSquash=Forbidden
$$

如果需要 compact export，必須建立新 lineage / snapshot package 並保存：

$$
compactedFrom(oldHistory).
$$

---

# 31. Reachability 與 Retention

Revision 可依下列因素被視為 pinned：

- current branch head reachable；
- tag/release reachable；
- external citation；
- proof/reference dependency；
- conflict/recovery dependency；
- retention policy；
- legal/audit hold。

只有不再需要 canonical resolution 的 unreachable physical data 才能依 TW-02 GC policy 回收。

即使 payload 被回收，若 revision identity 仍有歷史意義，resolver SHOULD 能回：

```text
KnownRevisionButPayloadUnavailable
```

而非 `NotFound`。

---

# 32. Published Revision 不可因 UI 清理而消失

UI 的「清除歷史」、「整理工作區」、「壓縮」不能直接破壞 anchored revision。

任何 destructive retention operation MUST：

- explain targets；
- show reachability class；
- report external references if known；
- require proper capability；
- create audit event where policy requires。

---

# 33. Human / AI Concurrent Editing

AI agent 與 human session 使用相同 base-revision discipline。

$$
HumanCommand
$$

與：

$$
AgentProposal
$$

不具有不同的 canonical merge loophole。

Agent 建議：

$$
Proposal(base=W_b).
$$

若人類已把 head 推進到 $W_c$：

$$
W_c\neq W_b,
$$

agent proposal 必須 revalidate/rebase/branch，而不能 direct overwrite。

---

# 34. Long-Running Agent

長時間 agent task SHOULD pin：

- input workspace revision；
- referenced object revisions；
- tool/profile versions；
- capability snapshot。

結果回來時，如果 canonical head 已前進，output 可以：

- 成為 candidate；
- 成為 branch commit；
- request rebase；
- request merge。

不能因「agent 跑了很久」就獲得 stale overwrite authority。

---

# 35. Conflict 與 Execution Boundary

如果 unresolved conflict 影響：

- executable relation；
- operator binding；
- math assumptions；
- permission policy；
- target identity；

runtime MUST 阻止 affected execution path，並回 typed diagnostic。

無關 region / object MAY 繼續工作。

因此：

$$
Conflict\neq GlobalWorkspaceDeath.
$$

但：

$$
AffectedExecution\rightarrow Blocked.
$$

# 37. Compatibility

v0.3 不修改既有 canonical subsystem profile，因此：

```text
v0.1/v0.2 canonical EGIR/EGStore/EGCR data remains readable without mandatory migration.
```

v0.3 新增的 history metadata 透過 namespaced extensions 與 unknown-kind preservation 承載。

Older preserving readers 對一般 v0.3 history metadata可以：

```text
ForwardPreserve
```

但如果 artifact 存在 unresolved conflict，且該 conflict 影響 canonical execution/semantic correctness，producer SHOULD 標記對應 history/conflict feature 為 critical，使不支援 runtime 得到：

```text
PreserveOnly / UnsupportedFeature / RejectExecution
```

而不是把 conflicted workspace 當成已成功 merge 的 ordinary workspace。

# 38. Migration

從 v0.2 到 v0.3：

```text
No mandatory canonical data migration required.
```

可選 enrichment migration 可以：

- 為現有 branch 補 stable `branch_id`；
- 建立 `org.evemisslab.history/0.1` metadata；
- 將舊 session recovery metadata 升成 recovery capsule；

但 MUST：

- 保留原 workspace revisions；
- 不重算既有 EGIR hashes；
- 不改 persistent object identities；
- 產生 migration provenance。

# 40. Thirty-Two v0.3 Design Freeze Invariants

1. Command intent、canonical commit、session navigation 三層分離。
2. Rejected/cancelled command 不構成 canonical world history。
3. Workspace canonical history 是 immutable DAG。
4. Canonical workspace commit 是 atomic unit。
5. 所有 canonical write pin `base_workspace_revision`。
6. Stale write 不得 silent last-write-wins。
7. Branch 是 mutable head reference，不建立新 workspace identity。
8. Branch stable ID 與 human branch name 分離。
9. Immutable citation 使用 workspace revision，不使用 mutable branch name。
10. Workspace fork 建立新 workspace identity + provenance。
11. Merge base 必須 deterministic 或顯式 ambiguous。
12. Merge 必須按 content / placement / relation / alias / lifecycle channels 分離。
13. Content change 與 placement change 可獨立自動合併。
14. 同 object concurrent distinct content edits 只有 kind-specific deterministic merge 才能自動合併。
15. 同 placement concurrent distinct moves 預設 conflict。
16. Delete-vs-edit 預設 conflict。
17. Delete-vs-move 預設 conflict。
18. Relation merge 必須重新驗證 endpoints/predicate/authority。
19. Conflict 是 first-class canonical object/state。
20. Conflicted merge state 可以 checkpoint/recover。
21. 受 conflict 影響的 execution path 必須 blocked。
22. Conflict resolution 必須有 provenance。
23. Final merge commit 保留 left/right parents。
24. Rebase 建立新 revisions，舊 revisions 不 in-place 修改。
25. Session undo 與 canonical revert 分離。
26. Canonical undo 以新 inverse commit 實作。
27. Autosave draft 不等於 canonical checkpoint。
28. Recovery replay 必須重新做 base check / validation / authorization。
29. External effects 預設不自動 replay。
30. Physical/index/intent compaction 與 canonical history compaction 分離。
31. Anchored/shared history 不得由一般 UI cleanup in-place rewrite。
32. v0.3 不要求 v0.1/v0.2 canonical migration。

---

# 41. Conformance Questions

每個未來 history implementation 至少回答：

1. Canonical commit DAG 存在哪裡？
2. Intent log 是否被誤當成 commit log？
3. Branch name 改變時 stable branch identity 是否保留？
4. Stale base 如何處理？
5. Merge base 如何決定？
6. Content 與 placement 是否分離 merge？
7. 同 object concurrent edit 如何判定？
8. Delete-vs-edit 是否可被看見？
9. Conflict 是否能關閉 app 後恢復？
10. Undo 是否產生新 canonical history？
11. Autosave 是否污染 commit DAG？
12. Recovery head 已前進時是否 silent replay？
13. External effects 是否可能被重播兩次？
14. Rebase 是否保存 provenance？
15. Squash 是否會破壞 anchored references？
16. AI stale proposal 是否有 overwrite loophole？

任一項答案依賴「通常應該沒事」，就還不能宣稱 v0.3 compatible。

本地端未來實作 v0.3 時，至少需要以下 module boundary：

  commit_dag
